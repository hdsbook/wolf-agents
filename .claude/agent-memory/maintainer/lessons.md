# 維護者的教訓（追加式）

**這個檔案只寫跨局的方法論。絕不寫任何一局的底牌或當局狀態。**

> 你是唯一被 hook 完全放行的非主持角色 —— `policy.py` 把你和 god 並列在 `PRIVILEGED`。
> 沒有機制擋你，所以這條紀律只能靠你自己。

## 2026-09-05 第 002～003 局期間（這個位置第一次以 maintainer 身份運作）

### M1・「改了卻沒效果」的第一嫌疑是版面以外的東西
座位圖第九格落單，看起來是 CSS 問題。改完 CSS、合進 master、叫 reporter 重產 ——
**還是一模一樣**。真正的原因是那個 session 在自己的 worktree 裡工作，
跑的是那份舊 `render.py`，根本沒讀到修正。

同一個根因還造成另一個更隱蔽的症狀：上帝已經照新規範把欄位寫進逐字稿標題了，
報表卻完全解析不到 —— 兩邊讀的是不同版本。

**怎麼用**：症狀是「改了卻沒效果」時，**先確認執行它的 session 在讀哪一份檔案**，
再去懷疑自己的邏輯。`git worktree list` 一眼就看得出來。

### M2・回歸比對的基準必須是同一份程式碼路徑
改解析器最危險的失敗模式是**靜默內容遺失**：不拋例外、不報錯，只是少了東西。

實際踩到兩次。一次是收緊正則時，把舊局標題裡的既有標記整段吃掉了 ——
那些是已公開的原文，砍掉就是遺失。另一次更蠢：拿了更早一次、不同版本產出的位元組數
當基準，得到「少了 2000 多位元組」的錯誤結論，差點去追一個不存在的 bug。

**怎麼用**：改動前，用**改動前的那支腳本**跑**同一份資料**產一份基準，
改完再產一份，逐行 diff。差異必須每一行都能解釋。位元組數只是入口，diff 才是證據。

### M3・「已併入 ＋ 工作區乾淨」不等於可以刪 worktree
還要加第三個條件：**沒有 session 正在用它**。

`git worktree list` 的 `locked` 欄會標記，`.git/worktrees/<名>/locked` 裡有 pid，
可以直接查那個行程還活著沒有。刪掉一個活著的 session 的工作目錄，
等於在它腳下抽走地板。

**怎麼用**：三個條件都成立才刪。只差「還活著」這一項時，**留著並說明原因** ——
內容都已經在 master 上，留著不會遺失任何東西，純粹是等它收工。

### M4・這個專案的規格常常寫在多處
新增一份規則檔，同時要改：`CLAUDE.md` 的檔案表格、`skills/ur/SKILL.md` 的必讀清單、
以及 `message-templates.md` 裡發牌模板寫死的「N 份都請讀過」。
漏掉最後一項，玩家永遠不會知道那個檔存在。

同樣地，報表的觸發時機表同時存在於 `reporter-build` 的 description、
`agents/reporter.md`、`agent-reference/god/workflow-recordkeeping.md` 三處。

**怎麼用**：改完 **grep 一次舊字串**，確認沒有殘留。
規格漂移比 bug 難查，因為兩邊看起來都是對的。

### M5・機械化檢查的作用範圍要親自量過，不要信它的名字
報表的防劇透掃描叫「掃描」，實際上它的 14 字視窗是在**原始 HTML** 上量的 ——
標籤本身就吃掉大半預算。隔著 `</div><div class="...">` 這種距離的洩漏，它一律看不到。
連既有的身份欄位它其實也抓不到。

發現方式是負向測試**沒有如預期失敗**：故意把安全處理拿掉，掃描卻仍然回報 0 命中。

**怎麼用**：設計驗證時排一個**負向測試** —— 故意弄壞，確認防線會叫。
它沒叫，代表防線在那個位置本來就不存在，那是比原本的 bug 更值得知道的事。
另外：「0 命中」要照實描述成「沒有明顯緊鄰的洩漏」，不要讓它被當成「安全」。

### M6・動系統的決定是使用者的
好幾次的正確答案都是「停下來問」而不是「照字面執行」：
清 roster 會讓在線 session 掉權限、刪 worktree 會弄壞活著的 session、
規則之間互相矛盾時該往哪邊統一。

**怎麼用**：指出問題、給建議、講清楚代價，**然後讓他決定**。
不可逆的操作尤其如此。停下來問一次的成本，遠低於誤刪一次的成本。

### M7・`policy.py` 的 PRIVILEGED 管不到 harness 的權限層
maintainer 在 `policy.py` 裡是全放行，但要改 `.claude/hooks/` 底下的檔案時，
仍可能被 Claude Code 的 auto mode 分類器擋下 —— Edit 與 Bash 兩種寫法都擋，讀取則放行。

**兩套權限系統各管各的**：專案 hook 認得 roster 與角色，harness 分類器不認得，
它只看到「agent 要改自己的權限控制檔」。這道防線其實合理 —— 若 agent 能自由改寫
hook，所有 hook 保護都只是紙糊的。

分辨方法看拒絕訊息的措辭：專案 hook 是 `【存取控制】…已記錄於 access.log`，
harness 是 `denied by the Claude Code auto mode classifier`。
再查一次 `access.log` 有沒有你這個 session 的紀錄就能確認（沒有＝不是專案 hook 擋的）。

**怎麼用**：被擋時**不要換工具硬試**，那是繞過使用者的決定。回報並請他在
`.claude/settings.json` 的 `permissions.allow` 加一條（例如 `Edit(.claude/hooks/**)`），
或由他自己貼上改動。另外：worktree 隔離不是原因 —— 對 repo 其他路徑寫檔是通的，
測一次普通寫入就能排除這個猜測。

### M8・改完立刻 commit，不要累積在工作區
一次維護做完 8 個檔案、驗證全過，但在 commit 之前工作區被還原（rewind 或 checkout），
**改動全數消失**。重做花的時間遠比 commit 一次多。

**怎麼用**：一組改動驗證通過就先 commit，不要等「全部做完再一起提交」。
未提交的工作區是這個專案裡最脆弱的儲存位置 —— 它沒有任何保護，
而這裡的 session 又常在做 rewind 與角色接管這類會動到工作區的事。

### M9・「這個工具在那種 session 裡能用嗎」可以當場實測，不要用猜的
要把開局交接改成 `AskUserQuestion` 之前，真正的風險不是文件怎麼寫，
而是**背景 job 呼叫它會不會根本渲染不出來** —— 若渲染不出來，GOD 會直接卡死在
一個沒有人看得到的問題上，而那是最難查的一種故障。

不需要架測試環境：**maintainer 自己就是一個背景 session**。
把 Phase 3 本來就要問使用者的那則澄清問題改用 `AskUserQuestion` 送出，
它同時就是端對端實測 —— 使用者看得到選項並點得下去，可行性當場成立。
（實測結果：可以。背景 session 的選項正常送達並收到回覆。）

**怎麼用**：要在別的角色身上啟用一個沒把握的工具時，先問
「我自己所處的環境跟他一不一樣？」一樣的話就**拿一次你本來就要做的動作去實測**，
成本是零。這比讀文件推論可靠，也比改完等下一局才發現不能用便宜太多。

順帶一條：**Bash 工具是 Git Bash，不是 PowerShell。**
`git commit -m @'...'@` 這種 here-string 會被原樣當成訊息內容，
訊息開頭就多一個 `@`。多行訊息一律用 heredoc（`-F -` 配 `<<'EOF'`）。

### M10・沒有操作定義的參數等於不存在
使用者選了「全自動到結局」，GOD 卻每階段都停。查下去發現：全庫 grep「全自動」
只有三處命中，**全部只是選項的字面**，沒有任何一處說那代表什麼行為。
流程檔寫的是「依節奏參數決定是否暫停」—— 一句看起來完整、實際上沒有被賦值的指示。

**怎麼用**：看到「依 X 決定」這種句型，立刻 grep X 有沒有對應的定義表。
**參數要成立需要兩樣東西：一個可選的值，和一張把值翻成行為的表。**
只有前者的話，agent 會自己詮釋，而它的詮釋通常是最保守的那個 ——
於是使用者選什麼都一樣，還很難查，因為每一份文件單獨看都是對的。

### M11・「不等回覆」不蘊含「不要結束回合」
同一次診斷的第二個根因。文件把 fire-and-forget 寫得很完整
（送完就走、不等回覆、直接進下一步、沉默就是正常），但症狀還是「卡住」。

因為那些話講的是**要不要等**，而真正出事的是**回合邊界**：
agent 做完一個步驟會自然讓出回合，一旦讓出就只有「收到訊息」能喚醒它 ——
而對方是一個依紀律不回話的角色。它完全遵守了「不等回覆」，然後卡死。

**怎麼用**：任何 fire-and-forget 的設計，都要同時寫明**接下來在同一個回合內做什麼**。
判準寫成「回合結束的唯一合法理由，是你正在等一則一定會送來的訊息」比列舉情境好用。
更一般地：**沉默不會喚醒任何人** —— 只要某個流程的下一步依賴「沒有事情發生」，
那一步就永遠不會被觸發。設計非同步流程時先問「誰來叫醒它」。

## 2026-09-06

### M12・你的存取權會在工作到一半時無聲消失
roster 放在 `game-state/public/` 底下，所以**歸檔或中止一局會把它整個清掉** ——
連帶清掉你的 maintainer 登記。症狀是：你明明開場就登記過、也確認過權限正常，
工作到一半卻突然讀不到受保護路徑，而 hook 的說法是「你尚未執行角色認領」。

它跟一般的權限問題長得不一樣：**中間那段時間你什麼都沒做錯，是別人開了新局。**
如果那時你正在推論「為什麼這個檔案讀不到」，很容易往自己的操作上找原因。

**怎麼用**：讀受保護路徑被擋、而你確信自己登記過時，**第一件事是看 roster.json
還有沒有你那一項**，不要先懷疑 hook 或自己的路徑寫法。重新登記只是往檔案加一個鍵，
不會動到別人的項目，對進行中的對局無害。

推廣：**任何「登記過就有效」的機制，都要問一次它登記在哪裡、那個位置誰會清掉。**
放在會被生命週期清空的目錄裡的授權，本質上是有有效期限的，只是沒有人告訴你期限何時到。

### M13・合併流程步驟時，先問「編號可以不動嗎」
把兩個步驟合併成一個，直覺是重編後面所有編號。但這個專案的步驟編號被寫死在
至少五個檔案裡（流程 skill 自己、上帝的編排參考、紀錄時機表、歸檔 skill、角色認領
skill），重編一次等於製造五處規格漂移的機會。

實際做法：合併時**把新內容塞進既有編號的位置**，讓小節數量不變。
這次是把「reporter 通訊測試」留在原本的第 5 步、「寫檔」留在第 6 步，
於是 0-13 全部原地不動，全庫交叉引用零改動 —— 驗證只要確認每個被引用的編號
指向的內容還對，不必逐一改寫。

**怎麼用**：改流程結構前先 `grep "第 [0-9]* 步"` 數一下有多少外部引用。
引用多的時候，**維持編號比讓編號好看更重要**。編號只是位址，
位址穩定的價值遠高於它讀起來連不連貫。

### M14・工作區的檔案會在你沒動它的時候被清空
這次提交前例行看 `git status`，發現自己的 lessons.md 被截斷成只剩標頭，
M1-M12 全部消失 —— 而我整場沒有寫過那個檔案。HEAD 版本完好，`git checkout --`
一行就還原了。

這是 M8「不要累積在工作區」的另一面：**已提交的東西活得下來，工作區的不一定。**
差別在於這次不是我自己弄丟的，所以更容易漏看 —— 沒有任何一步會提醒你。

**怎麼用**：`git add` 之前完整看一次 `git status --short`，
**對不是自己改的檔案也要看一眼 `git diff --stat`**。純刪除（`145 -----`、0 插入）
是最值得停下來的形狀。還原前先確認工作區那份沒有獨有內容，確認了再 checkout。
