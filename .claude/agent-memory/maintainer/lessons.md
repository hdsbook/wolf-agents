# 維護者的教訓（追加式）

**這個檔案只寫跨局的方法論。絕不寫任何一局的底牌或當局狀態。**

## 2026-09-06

### M13・合併流程步驟時，先問「編號可以不動嗎」
把兩個步驟合併成一個，直覺是重編後面所有編號。但這個專案的步驟編號被寫死在
至少五個檔案裡（流程 skill 自己、上帝的編排參考、紀錄時機表、歸檔 skill、角色認領
skill），重編一次等於製造五處規格漂移的機會。

實際做法：合併時**把新內容塞進既有編號的位置**，讓小節數量不變。
這次是把「reporter 通訊測試」留在原本的第 5 步、「寫檔」留在第 6 步，
於是 0-13 全部原地不動，全庫交叉引用零改動 —— 驗證只要確認每個被引用的編號
指向的內容還對，不必逐一改寫。

**怎麼用**：改流程結構前先 `grep "第 [0-9]* 步"` 數一下有多少外部引用。
引用多的時候，**維持編號比讓編號好看更重要**。編號只是位址，
位址穩定的價值遠高於它讀起來連不連貫。

### M14・工作區的檔案會在你沒動它的時候被清空
這次提交前例行看 `git status`，發現自己的 lessons.md 被截斷成只剩標頭，
M1-M12 全部消失 —— 而我整場沒有寫過那個檔案。HEAD 版本完好，`git checkout --`
一行就還原了。

這是 M8「不要累積在工作區」的另一面：**已提交的東西活得下來，工作區的不一定。**
差別在於這次不是我自己弄丟的，所以更容易漏看 —— 沒有任何一步會提醒你。

**怎麼用**：`git add` 之前完整看一次 `git status --short`，
**對不是自己改的檔案也要看一眼 `git diff --stat`**。純刪除（`145 -----`、0 插入）
是最值得停下來的形狀。還原前先確認工作區那份沒有獨有內容，確認了再 checkout。

### M15・合併步驟之後，要回頭問舊機制「你還需要嗎」
`ping_reporter` 是在「發牌」與「派 reporter 初始化」還沒合併時設計的，
當時 reporter 確實需要一則專屬訊息才驗得到出站。合併之後，派工那一則
加上他的回報已經完整涵蓋同一件事 —— 但沒有人回頭問這句話，
於是同一條線被驗了兩次，還多一個上帝可能卡住的往返。

**冗餘不會報錯。** 它不像規格漂移會產生矛盾，所以 grep 一致性檢查抓不到它 ——
它每一處都寫得對，只是整件事已經不必做了。

**怎麼用**：每次合併訊息或步驟之後，拿舊機制的名字（模板名、action 名、步驟標題）
grep 一次，逐一問「新機制是否已經涵蓋它證明的東西，而且證明得更多」。
這次的答案是「是」：一句「reporter 就位」只證明線通，
而「開局初始化完成」同時證明線通、skill 跑得動、檔案寫得出來。

刪掉之後**要在原位留一句話說明為什麼不做**（本次保留了 `/god-open` 第 5 步的編號，
內容改寫成「這一步不發訊息」）—— 否則下一個讀到流程的人會憑印象把它加回來。

### M16・拆檔要「逐段對本文」，不是對行數或位元組
把一份大模板檔拆成七份時，最危險的失敗模式和改 `render.py` 一樣是**靜默內容遺失**。
行數、位元組、action 數量全部對得上，中間少一段照樣看不出來
（而且 CRLF→LF 會讓位元組數本來就對不上，見環境事實）。

實際做法：**用程式重建「拆檔前」的內容，切成 `{action: 本文}` 兩邊逐字比對**。
這次是 `git show HEAD:<檔>` 再套上我自己先前那一次編輯。
第一次跑就抓到一個差異 —— 結果是我**到之前就存在的未提交修改**，不是拆檔造成的。
那次「誤報」本身就是這個方法的價值：它逼我去確認差異的來源，而不是憑感覺放行。

**怎麼用**：任何搬運型改動（拆檔、合檔、換目錄）都先建立可比較的基準再動手。
基準必須是「改動前的同一份內容」；拿 HEAD 直接比會把別人未提交的修改誤判成你弄丟的東西。

### M17・Markdown 圍欄裡還有圍欄時，外層要用四個反引號
拆檔後寫了一支腳本抓「標題之後第一個 ``` 區塊」當模板本文，`deal` 立刻被切在半路 ——
它的內文本身就含有 ``` （它要玩家建立檔案，示範了檔案內容）。

CommonMark 的規則是 **N 個反引號開的區塊，要 >= N 個反引號才關得掉**，
所以外層改成四個反引號 ```` 就正確了，內層原文一個字都不用動。

**怎麼用**：任何要用程式解析 Markdown 圍欄的地方，先掃一次每個區段裡有幾個圍欄 ——
超過兩個就是有巢狀。解析器照 N/>=N 規則寫，不要寫成「配對第一個和第二個」。

### M18・並行的兩邊，不能互相驗對方「正在寫」的欄位
reporter 幾乎每一局都會在天黑之前抓到同一項不一致：`02-status.md` 的進度停在發牌前，
而底牌已經存在。每次上帝都更新了，下一局又發生 —— 那就不是疏忽，是流程有洞。

根因是一組時序矛盾：上帝在**第 6 步**（洗牌前）寫進度，`reporter-init` 卻要求
「下一步＝第 1 夜」，而 `reporter-init` 是**與發牌並行**跑的。
reporter 讀那個欄位時，上帝根本還沒有資格把它改成第 1 夜 ——
**他讀到的必然是舊值，而且他每一次都是對的。**
每個階段的 skill 結尾都有「更新 02-status」，唯獨開局沒有，因為開局把寫檔排在第 6 步、
事實卻一路走到第 9 步。

修法兩件事：**(a)** 在事實變化的當下補上寫檔點（廣播完立刻覆寫進度區塊）；
**(b)** 把那一項檢查移給**擁有第一手資料的人** —— 「現在走到哪一步」是上帝知道的，
不是 reporter 能從檔案反推的。reporter 換成驗「座位表與底牌一致」，
那份檔在他開工前就寫好了，不會在他腳下變動。

**怎麼用**：設計並行的兩個 agent 時，逐項問「這個欄位在檢查的那一刻，另一邊寫完了嗎」。
沒寫完就不是他能驗的東西 —— 交給寫的人自驗，或改驗一個**在他開工前就凍結**的欄位。
一個每局都復發、每局都被「修好」的不一致，幾乎一定是時序問題，不是紀律問題。

順帶一條判準：**每個階段的結尾都有寫檔點，只有某一個階段沒有** —— 那個缺口就是答案。
盤點時用「同一件事在別的階段是怎麼做的」去對照，比盯著出問題的那一處看有效得多。

### M19・分類的軸選錯，整個安全設計就會蓋在錯的地方
把公版廣播改成落檔時，第一直覺是照「公版 vs 私訊」分 —— 公版落檔、私訊直送。
那個軸是錯的，而且錯得很隱蔽：**收件人本身就可能是機密**。
`night_seer` 發給誰，就等於公布了預言家是誰；`hunter_shot` 同理。
照「公版/私訊」分，這兩則會因為「內容只是問你要查誰」而被歸成可落檔，
於是「哪個檔存在」直接洩漏神職。

正確的軸是**含不含機密，而且要把收件人算進去**。換了軸之後結論也變了：
`ask_speak` 看起來很像私訊（一人一份、內容各不相同），但它的每一個欄位
——順位、必讀清單、落檔路徑——全部本來就公開，所以它是可落檔的，
而且它是**每天量最大的一則**（9 位 × 740 字）。軸選對，最大的那塊才會落在對的邊。

**怎麼用**：要把一批東西分成「安全」與「不安全」時，先明確寫下判準是什麼，
再拿**最像反例的兩個**去試（這次是 `hunter_shot` 與 `ask_speak`）。
兩個都分對了，軸才是對的。分完再回頭看：量最大的那一塊落在哪一邊？
若最大的那塊落在「不安全」，多半是軸選錯了，不是它真的不安全。

### M20・安全邊界要編進機制，不要只寫在文件裡
可落檔的清單同時存在兩處：`god-dispatch/SKILL.md` 的表格（給人看）
與 `render.py` 的 `FILE_OK`（給機器擋）。**後者才是保證。**
上帝只要對含機密的 action 下 `--out`，腳本就拒絕、一個檔都不產生 ——
不必依賴他有沒有讀到表格、有沒有讀懂。

這跟這個專案既有的做法是同一路：路徑保護不靠自律，靠 hook 實際攔截。

**怎麼用**：每寫一條「不可以做 X」的規則，問一句**「誰會擋住它」**。
答案是「讀到的人自己」就代表它只是文件；能指出一個會回傳錯誤的地方，它才是機制。
文件那份不是多餘的 —— 它解釋為什麼 —— 但兩份要同時存在，而且要說清楚哪一份是權威。

### M21・要機器可讀的格式，就讓「產生的那一端」是腳本，不要叫人手寫 JSON
想讓 reporter 用腳本併發言時，直覺是改玩家的落檔格式 —— 叫他們寫 JSON，
reporter 就不必解析。**那個方向會把成本轉嫁到最不該承受它的一端。**

玩家寫的是散文，裡面有引號、換行、全形符號。要 LLM 手寫合法 JSON
就是引進一種新的失敗模式，而且**這種失敗沒有復原路徑** —— 純文字檔不可能解析失敗，
壞掉的 JSON 會讓那則發言整個進不了逐字稿。反過來看收益：reporter 真正需要的
結構化資訊（天數、輪次、座位）**本來就寫在檔名裡**，宣告在最後一行，
腳本自己就抽得出來，玩家端一個字都不必改。

**怎麼用**：問「這個結構化資訊，能不能由讀的那一端自己推出來」。
能，就不要去改寫的那一端的合約 —— 尤其當寫的那一端是人或 LLM。
把 JSON 當成**中間格式**（腳本產生、腳本消費），不要當成輸入格式。

### M22・換解析器時最強的測試是「同一份資料走兩條路徑」
`render.py` 改成優先讀 JSON、找不到才解析 Markdown 之後，怎麼證明沒改壞？
單看新路徑的產出「看起來對」證明不了什麼 —— 靜默內容遺失正是看起來對的。

做法是**讓同一份資料走兩次**：帶著 JSON 渲染一次存起來，把 JSON 刪掉再渲染一次，
兩份 HTML 逐行比對。相同就代表新路徑沒有多出、也沒有少掉任何東西。
再加一道：拿一份**歷史歸檔**（沒有 JSON）跑，與改動前的基準比對，
確認舊路徑零影響。兩道合起來，新舊都被釘住了。

**怎麼用**：任何「新增一條快速路徑、保留舊路徑當 fallback」的改動，
都要能建構出這種 A/B。建構不出來（例如兩條路徑吃的不是同一份資料），
那就代表它們其實不等價，**那才是真正要停下來的訊號**。
