# 維護者的教訓（追加式）

**這個檔案只寫跨局的方法論。絕不寫任何一局的底牌或當局狀態。**

> 你是唯一被 hook 完全放行的非主持角色 —— `policy.py` 把你和 god 並列在 `PRIVILEGED`。
> 沒有機制擋你，所以這條紀律只能靠你自己。

**新增教訓**：在 `lessons/` 新增一檔，四欄格式（結論／原因／來源／怎麼用），並在本索引加一行。

---


## 2026-09-06

- [M13・合併流程步驟時，先問「編號可以不動嗎」](lessons/M13-合併流程步驟時先問編.md) — 改流程結構前先 grep "第 [0-9]* 步" 數一下有多少外部引用。
- [M14・工作區的檔案會在你沒動它的時候被清空](lessons/M14-工作區的檔案會在你沒.md) — git add 之前完整看一次 git status --short，對不是自己改的檔案也要看一眼 git diff --stat。
- [M15・合併步驟之後，要回頭問舊機制「你還需要嗎」](lessons/M15-合併步驟之後要回頭問.md) — 每次合併訊息或步驟之後，拿舊機制的名字（模板名、action 名、步驟標題）grep 一次，逐一問「新機制是否已經涵蓋它證明的東西，而且證明得更多」。
- [M16・拆檔要「逐段對本文」，不是對行數或位元組](lessons/M16-拆檔要逐段對本文不是.md) — 任何搬運型改動（拆檔、合檔、換目錄）都先建立可比較的基準再動手。
- [M17・Markdown 圍欄裡還有圍欄時，外層要用四個反引號](lessons/M17-Markdown圍欄.md) — 任何要用程式解析 Markdown 圍欄的地方，先掃一次每個區段裡有幾個圍欄 ——超過兩個就是有巢狀。
- [M18・並行的兩邊，不能互相驗對方「正在寫」的欄位](lessons/M18-並行的兩邊不能互相驗.md) — 設計並行的兩個 agent 時，逐項問「這個欄位在檢查的那一刻，另一邊寫完了嗎」。
- [M19・分類的軸選錯，整個安全設計就會蓋在錯的地方](lessons/M19-分類的軸選錯整個安全.md) — 要把一批東西分成「安全」與「不安全」時，先明確寫下判準是什麼，再拿最像反例的兩個去試（這次是 hunter_shot 與 ask_speak）。
- [M20・安全邊界要編進機制，不要只寫在文件裡](lessons/M20-安全邊界要編進機制不.md) — 每寫一條「不可以做 X」的規則，問一句「誰會擋住它」。
- [M21・要機器可讀的格式，就讓「產生的那一端」是腳本，不要叫人手寫 JSON](lessons/M21-要機器可讀的格式就讓.md) — 問「這個結構化資訊，能不能由讀的那一端自己推出來」。
- [M22・換解析器時最強的測試是「同一份資料走兩條路徑」](lessons/M22-換解析器時最強的測試.md) — 任何「新增一條快速路徑、保留舊路徑當 fallback」的改動，都要能建構出這種 A/B。
- [M23・工作要推到「已經擁有那份資訊的那一端」](lessons/M23-工作要推到已經擁有那.md) — 看到「同一件事重複 N 次、每次幾乎一樣」時，先問變的是什麼。
- [M24・能算出來的欄位，不要要求上游填](lessons/M24-能算出來的欄位不要要.md) — 每個要人填的欄位都問一次「這個值是不是別的欄位的函數」。
- [M25・hook 指令的路徑要用 $CLAUDE_PROJECT_DIR，不要用相對路徑](lessons/M25-hook路徑用專案變數.md) — 改 hook 路徑後從子目錄再跑一次受管工具，確認 hook 還找得到腳本。
