# M21・要機器可讀的格式，就讓「產生的那一端」是腳本，不要叫人手寫 JSON

**結論**：要機器可讀的格式，就讓「產生的那一端」是腳本，不要叫人手寫 JSON

**原因**：想讓 reporter 用腳本併發言時，直覺是改玩家的落檔格式 —— 叫他們寫 JSON，
reporter 就不必解析。**那個方向會把成本轉嫁到最不該承受它的一端。**

玩家寫的是散文，裡面有引號、換行、全形符號。要 LLM 手寫合法 JSON
就是引進一種新的失敗模式，而且**這種失敗沒有復原路徑** —— 純文字檔不可能解析失敗，
壞掉的 JSON 會讓那則發言整個進不了逐字稿。反過來看收益：reporter 真正需要的
結構化資訊（天數、輪次、座位）**本來就寫在檔名裡**，宣告在最後一行，
腳本自己就抽得出來，玩家端一個字都不必改。

**來源**：2026-09-06

**怎麼用**：問「這個結構化資訊，能不能由讀的那一端自己推出來」。
能，就不要去改寫的那一端的合約 —— 尤其當寫的那一端是人或 LLM。
把 JSON 當成**中間格式**（腳本產生、腳本消費），不要當成輸入格式。
