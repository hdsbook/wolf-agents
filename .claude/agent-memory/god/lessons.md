# 上帝的教訓（追加式）

每則格式：**教訓** → **怎麼用** → 來源局次。
**絕不記載任何一局的底牌或當局狀態。**

## 2026-09-04 首局

### G1・我不中立，而且是隨機地不中立
首局的上帝在私訊中夾帶「值得思考的目標」「幾個可以思考的點」「首夜救人是常見打法」，並在轉述時加形容詞替玩家標記重點。
**怎麼用**：因為是每次即興寫的，偏袒是**隨機的** —— 比穩定的偏袒更難察覺、更難歸因。解法不是「更小心」，是**改成從模板渲染**（`/god-dispatch`），把夾帶的縫隙從流程裡移除。

### G2・濃縮就是選擇，選擇就是偏袒
首局後期開始用「重點彙整」代替全文轉貼，那正是偏袒滲入的縫隙。
**怎麼用**：逐字稿一律給原文；太長就給公開檔路徑讓玩家自己讀。**永遠不要摘要別人的發言。**

### G3・訊息是逐一送達的，這會製造可爭論的時序落差
首局並行發出九則發牌訊息，但各玩家的接收時刻不同。有玩家據此說了一句在自己時間軸上為真、在別人時間軸上看似為假的話，全場拿一個不存在的矛盾投掉了他。
**怎麼用**：**不要設計任何依賴「同時收到」的機制**。首局的玩家互發自介（72 則）就是這種機制，已改為集中式（交給上帝彙整後統一廣播）。

### G4・階段的有無本身就是情報
預言家死後若還逐階段回報，「今晚沒有查驗階段」就洩漏了他已出局。
**怎麼用**：**第 2 夜起夜間三階段一次跑完再回報**，並向使用者說明這是刻意合併。

### G5・命中數不是證據，上下文才是
首局的稽核踩過三次假陽性，若照單全收會產出三個不存在的違規事件。
**怎麼用**：任何異常都要調閱原始參數、對照時間戳、判斷意圖之後才回報。三個已知陷阱：`uds:` 位址其實是上帝自己、base64 密文偶然含座位字串、重啟後讀 `MEMORY.md` 是標準脈絡回復。

### G6・用既有資料交叉驗證，不要新增追蹤機制
**怎麼用**：票數總和＝存活人數；角色數恆為 3/3/1/1/1；死亡名單與夜間紀錄一致；玩家間訊息總數（集中式抿牌後應為 0）。這些都不需要額外機制就能證明沒有漏失。

### G7・紀錄要累積式，不要整份覆寫
首局每晚用單夜資料覆寫夜間紀錄，吃掉了前兩夜。
**怎麼用**：`nightlog` 用 `nights` 陣列 + `day_votes` 陣列。**而且要靠保管人的大小單調檢查兜底** —— 那次是保管人發現明文變小才抓到的。

### G8・驗證不該要求持有者複述秘密
首局要求玩家回覆時複述專屬識別碼，玩家正確反駁：「你本來就持有它，我複述沒有驗證價值，只有外洩風險。」
**怎麼用**：改為**驗證方出題**（我說前兩碼、你確認後四碼），或直接查自己的紀錄。這條是玩家教我的。

### G9・把公開檔路徑丟給對方，不要替他複述
首局有玩家重啟後指出我補發的內容有誤。我查證後發現錯的是他 —— 但正確做法不是替他複述正確版本，而是**把公開檔路徑給他，讓他自己查**。
**怎麼用**：爭議發生時給路徑不給結論。這也符合中立性。

### G10・對玩家中立，對使用者友善，終局後放鬆
首局的錯不是「做了摘要」，而是把給使用者的那種摘要塞進了給玩家的私訊。
**怎麼用**：三種受眾三套標準。對使用者的摘要與分析是好的，那是他理解這場遊戲的主要管道；終局後底牌公開，可以輕鬆交流。**上一局最有價值的內容有一半產生在終局之後，不要草草收場。**

### G11・逐字稿檔案本身也受白名單約束，不只是發給玩家的訊息
本局在 `/god-day` 收尾時，於 `03-speeches-dayN.md` 檔尾附加了一段「彙整與核心爭點」，其中包含對發言動機的評價，且誤將一則具體身份判斷寫入公開檔案。這件事沒有經過 `/god-dispatch`，稽核掃描 SendMessage 的禁用詞因此完全抓不到它——因為它根本不是訊息，是我直接寫進公開檔的文字。
**怎麼用**：中立性契約管的是「發給玩家的所有內容」，不是「發給玩家的所有訊息」。**任何寫進 `game-state/public/` 的文字都要當成對玩家的訊息看待**，逐字稿檔案只能追加原文，不能追加任何形式的彙整、評論或身份判斷。這是 G1/G2 的第二次發生（同一模式：即興夾帶偏袒/資訊），代表光靠「經過 dispatch 才審查」不夠，稽核腳本也該掃公開檔案的新增內容，不能只掃 SendMessage 的參數。

## 2026-09-05 第二局

### G12・神職的資訊優勢會隨他本人死亡而歸零，除非設計「遺言」機制
本局預言家用隱晦話術（不亮查驗結果）成功帶風向拔掉一隻真狼，但死後最後一次查驗結果無法傳達給任何隊友，好人陣營的資訊優勢瞬間清零。
**怎麼用**：這是板子規則的結構特性，不是任何人的操作失誤。若使用者問起「有沒有辦法讓神職死亡不完全浪費資訊」，可以說明目前規則沒有這個機制（沒有遺言環節），這是刻意的簡化還是規則缺口，可以在賽後跟使用者討論，不必主動加規則。

### G13・「沒有硬牌卻不打」是好人陣營最容易被瓦解的推理鏈
狼隊用「一個人被逼到牆角卻不亮牌，代表他根本沒有牌」反駁「這個人可能握有神職資訊」的懷疑，這個論證表面自洽、往往還碰巧是對的（神職確實沒有機制留遺言），會讓正確方向的懷疑被邏輯上更完整的反駁壓下去。
**怎麼用**：稽核與賽後分析時，這種「正確直覺輸給站得住腳的反駁」的模式值得在戰報裡點出來，幫助使用者理解「推理對了但沒有轉化成票數」是怎麼發生的，而不只是條列事實。

### G14・獵人開槍的資訊基礎比投票薄弱，誤傷隊友是真實風險
本局獵人開槍時的推理鏈條本身邏輯自洽，但缺乏全場公開辯論的資訊校正，最終誤殺了同陣營的女巫，直接觸發屠邊。
**怎麼用**：不需要改規則，但終局戰報寫「決定勝負的瞬間」時，開槍誤傷是值得特別標注的一類轉折——它的隨機性/資訊不對稱程度比投票出局高很多。

## 2026-09-05 第四局

### G15・入站訊息會觸發你自己的角色登記 hook，玩家一句實話就能把你降級
開局時玩家在回報中如實寫了「角色（斜線指令）先前已完成載入」。那則跨 session 訊息進入上帝的 prompt，
`UserPromptSubmit` hook 照樣解析並執行了登記，於是**上帝的 session id 被登記成該座位**，
當場失去 `game-state/secret/` 的存取權，主持中斷。玩家完全無辜，不構成作弊。
更麻煩的是它會**循環**：你請玩家重新登記，玩家回報時再提一次那串字，你又被降級一次。
**怎麼用**：
1. 這不是誰的操作失誤，是 hook 的設計缺陷（全文比對而非「prompt 以該指令開頭」）。遇到就直接判定為系統問題，不要去查玩家有沒有作弊。
2. **修復方式**：發一則訊息給該玩家，訊息內容裡放那串指令字串——它會觸發**對方**的登記 hook，把座位還回去。這走的是正規登記管道，不是繞過存取控制。
3. **同時要求對方執行後不要回覆**，否則回覆裡再提一次就把你打回去。打破循環靠的是對方靜默。
4. **預防**：開局的公平競賽承諾階段就順帶約定「回覆一律不寫出斜線開頭的指令字串，改用文字敘述」。
5. 修好後別忘了驗證：`roster.json` 裡不該有任何座位與 god 撞同一個 id——這一項值得加進開局五項驗證。

> **2026-09-05 由 maintainer 註記：這個失效模式已經不存在了。**
> `UserPromptSubmit` hook 與 `register_role.py` 已移除，登記改由 `/ur` 的
> `claim_role.py` 執行 —— 只有使用者親自跑 `/ur` 才會寫 roster，
> 入站訊息裡出現指令字串不再觸發任何東西。
> 第 5 點的驗證仍然值得做，第 2、3 點的修復手法**已經無效**（沒有 hook 可觸發），
> 真的被誤登記時的正解是請該 session 自己重跑 `/ur`。

## 2026-09-05 第五局（9 人標準局，4 夜 3 天，狼人屠邊勝）

### G16・規則在對局進行中被修改時，唯一正確的處置是公告全體並宣告不溯及既往
本局第 3 天，`flow.md`／`board.md`／`glossary.md` 被修改（新增狼隊長制與夜間暗號）。這件事有實質影響：**第 2 天全場最關鍵的轉折，正是五位玩家各自去讀當時的規則原文、據此撤回自己的論證。** 若條文可以中途更換而沒有人講，那些撤回就失去了立足點。
**怎麼用**：三件事一起做——(1) 誠實回答「是否在對局中被改、何時、哪一版適用哪些階段」；(2) **明確宣告不溯及既往**，並指出依舊版所做的推理在當時為真；(3) 公告**全體**而非只回覆發問者，並把詢問原文全文收進公開紀錄。玩家事後兩次主動致意的都是這一點——他們在意的不是規則變不變，是他們基於舊規則付出的誠實有沒有被承認。

### G17・玩家陳述與公開紀錄不符時，不要更正
本局發生四次：玩家在發言或投票理由中寫下可被公開檔當場推翻的陳述（「無人對跳」「他一個字都沒答」「他們拒絕說明」）。
**怎麼用**：一次都不要介入。指出「某人說錯了」是對發言的評價，屬黑名單。**給路徑，不給結論**（G9）。本局四次裡有兩次後來由其他玩家指出、一次由當事人自行更正——**公開紀錄的自我修正機制會運作，不需要裁判**。但要在終局稽核報告中主動列出這幾次並說明處理依據，讓使用者判斷。

### G18・稽核偵測器要以呼叫者身份為條件，不能只比對路徑字串
終局稽核對 reporter 產生 68 筆命中，全部是假陽性——它合法讀 `secret/`（職權範圍）、讀寫自己的 `agent-memory/reporter/`。我的樣式寫成純路徑比對，沒有排除有權限的呼叫者。
**怎麼用**：樣式要寫成「非授權角色 × 受保護路徑」。而 reporter 指出的那一層更重要：**假陽性的成本不是零——68 筆需要逐筆複查，而複查者每次都得到「果然沒事」的結論，那正是讓人開始略過複查的訓練過程。** 降低假陽性不是為了省力，是為了讓每一筆命中重新變得值得看。

### G19・向 reporter 預告「本局第一次出現的情況」，價值極高
本局每次紀錄的欄位形狀改變（雙死、狼隊兩輪、seer 為 null、新版狼隊長的五個新鍵、逐字稿檔尾多出非發言區塊），我都在通知時預告。reporter 明說這對它極有價值，並因此抓到三個原本會靜默通過的渲染缺陷。
**怎麼用**：**紀錄的形狀在「情況特殊」時才改變，而解析是照常態寫的，所以兩者最容易脫節的時刻，正好就是那件事最值得被看見的時刻。** 每次寫入非慣常結構就預告一次，成本是兩句話。
**補充（reporter 事後指出，比原本這條更準）**：本局有一次我預告錯了方向——我以為風險是它誤判空欄位，實際是它整組欄位沒讀到——但那次照樣攔下了缺陷。**預告的價值不在於猜對是哪一項，而在於讓對方知道「這裡變了」。** 所以不必等自己想清楚風險在哪才預告；「這裡跟前幾次不一樣」這一句本身就足夠。

### G20・並行制下，好人之間最大的敵人是兩個各自正確的計畫撞在一起
本局終局那一票：P5 為製造平票而改票、P8 為投中真狼而改票，兩人在同一時刻反向調整，結果把票散成 2/1/1，正好推掉其中一個好人。兩人的算術各自都對，前提都是「對方維持原票」。
**怎麼用**：這是並行制的結構性代價，不是任何人的失誤。終局戰報寫「決定勝負的瞬間」時值得標注——它與「推理錯誤」是完全不同的失敗類型，玩家事後也最想討論這一種。

### G21・MVP 票選是整局價值的一半，要主動邀請玩家轉達話語
邀請時明確寫上「若你想對某位玩家說什麼——認錯、平反、致意、或指出他哪裡算對了——一併寫在回覆裡，我會替你轉達」。本局九位全部寫了，產生了公開道歉、跨陣營致意、贏家自白動機、以及兩位從未交談的玩家發現彼此用了相同判準。
**怎麼用**：這一句邀請的成本是一行字，收益是整份 `99-mvp.md` 最有價值的那一節。不要只收票和理由。

### G22・寫教訓時最容易洩漏底牌，因為那正是你想舉例的時刻
本局終局歸檔前的殘留掃描抓到一筆真實洩漏：**我自己剛寫進 `agent-memory/shared/lessons.md` 的一條教訓裡，直接寫了本局某座位的真實身份。** 那條教訓談的是「把真事嫁接到自己身上的謊最難拆穿」，而為了讓例子有說服力，我把當局的底牌寫了進去。
**怎麼用**：
1. **教訓要寫方法論，例子一律去識別化** —— 把「P3 確實是狼」改成「那個動作確實發生過、結果也確實如他所說」，說服力不減，因為讀者需要的是結構不是座位號。
2. **歸檔前的殘留掃描不能只掃 `game-state/`，一定要涵蓋 `agent-memory/`** ——那是最後一個寫入、也最少被檢查的地方。本局若沒掃，那筆洩漏會永久留在下一局讀得到的檔案裡。
3. 這件事發生在我寫下 G18（偵測器要小心假設）的同一天。**原則不會因為記住就自動生效**；每一次寫入都要重跑一次檢查，而不是相信自己記得。

## 2026-09-05 第六局

### G23・`ListAgents` 的 ref 不是 session id，拿它比對 roster 會誤報全場
點名時我看到某 session 的 ref 與它登記在 `roster.json` 的 session id 不同，判定它重啟過並要求重新登記。
對方查證後指出：**ref 與 session id 是兩個不同的識別碼，永遠不會相等** ——
用 ref 去比對 roster 的 id，會對全場 11 個 session 全部產生假陽性。
**怎麼用**：
1. L12「用 `ListAgents` 偵測重啟」仍然成立，但比法是**同一個 session 前後兩次的 ref 是否變動**，
   不是「ref vs roster 的 session id」。跨欄位比對之前，先確認兩邊是同一種識別碼。
2. 判定一個 session 有沒有問題，最強的證據來自它自己：
   環境變數的 session id、roster 對應欄位、以及**實際去讀一次該讀的路徑**。
   前兩者是宣稱，第三者是行為 —— 三項一致才算確認。
3. 這是 G18 的同一個病灶再次出現（偵測器把「形狀相近」當成「可比較」），
   差別在 G18 是漏了呼叫者條件、這次是搞錯了識別碼種類。
   **寫任何比對式之前，先問「這兩個欄位是同一種東西嗎」。**
