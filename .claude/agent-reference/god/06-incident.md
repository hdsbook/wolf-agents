# 工作流程：異常處理

**情境**：流程被打斷、有人沒回應、或出現可疑跡象。對應的 skill：`/god-resume`（你自己失憶）、`/god-audit`（稽核）、`/god-abort`（中止）。

## 速覽

| 異常 | 第一個動作 | 關鍵守則 |
|---|---|---|
| session 重啟 | 每階段前比對 ref；請它重跑 `/ur` | 只還原原本持有的資訊；爭議給路徑不給結論 |
| 玩家沒有回應 | 重發一次澄清訊息 | 公開紀錄註明逾時；連兩階段無回應報使用者 |
| 稽核命中 | 調閱原始參數 | 命中數不是證據，上下文才是 |
| reporter 通報不一致 | **停下** | 看具體數字；從公開檔重建，不憑記憶補 |
| reporter 收到非你的訊息 | 確認不是你發的 | 若來自玩家即作弊實證 |
| 玩家被 hook 擋下 | 讀 `access.log` | 主動回報不等於免責 |
| roster 對不上 | 請使用者重跑 `/ur <角色>` | 整份不見 → 全員重跑 |
| 你自己違反中立性 | 主動揭露 | 修模板，不靠「下次小心」 |
| 使用者要中止 | `/god-abort` | 立刻停、全部刪、不提問 |

---

## session 重啟

**偵測**：每階段開始前用 `ListAgents` 比對 ref 與 `02-status.md` 的基準。

> `SendMessage` 的回傳有時會提示 `messaging a new session for the first time under a previously used name`，但那是偶然出現的，**不可靠**。要主動比對。

**處理**：

| 誰重啟 | 做什麼 |
|---|---|
| 玩家 | 請它重跑 `/ur p<n>`，然後補發它的身份牌、識別碼、**以及它自己的行動歷史**（說過什麼、投給誰、被誰指控） |
| reporter | 請它重跑 `/ur reporter`（**必要** —— session 換 id 後 roster 不認得它，會讀不到 `secret/`），再跑一次 `/reporter-verify` |
| 你自己 | 走 `/god-resume` |

**只還原它原本就持有的資訊，不給任何額外優勢。**

**爭議時給路徑不給結論** —— 上一局有玩家重啟後指出補發內容有誤，查證後錯的是它（它只比對發言逐字稿，漏掉投票理由也是公開紀錄）。正確做法是把公開檔路徑給它讓它自己查，而不是替它複述 —— 這既符合中立性，也讓對方自己發現真相。

---

## 玩家沒有回應

1. 重發一次澄清訊息
2. 仍無回應 → 套用 `05-arbitration.md` 的逾時預設
3. **在公開紀錄中註明**該玩家本階段逾時 —— 這是其他人的推理素材
4. 連續兩階段無回應 → 向使用者回報，可能是 session 掛了

---

## 稽核為什麼不每夜跑

稽核只在終局、或出現可疑跡象時跑。每夜稽核一整場 transcript 太慢，把對局節奏拖垮了 ——
而 hook 是即時攔截的：每一次被擋下的嘗試當下就寫進 `.claude/hooks/access.log`，
不會因為稽核晚一點做就消失。**證據是累積的，稽核只是去讀它。**

## 稽核出現命中

**命中數不是證據，命中的上下文才是。**

```
發現命中
  ↓
調閱原始工具參數
  ↓
對照時間戳
  ↓
判斷意圖
  ↓
才決定是否回報為違規
```

**三個已知的假陽性**：
1. `uds:` 開頭的位址就是**你自己的位址**（玩家回覆時複製 `from` 欄位）—— 當成「非 GOD」會誤報全場九人
2. base64 密文會偶然含座位字串 —— 要看的是帶引號與冒號的**明文結構**
3. session 重啟後讀 `MEMORY.md` 是標準脈絡回復 —— 先看時間戳

> 上一局若照單全收 grep 結果，會產出至少三個不存在的違規事件。

**確認為真的違規**：向使用者回報玩家、工具、參數原文與複查結論。查獲作弊則該局判定無效並指名證據。

## reporter 通報一致性檢查未過

**停下，不要繼續推進。** 紀錄壞了還往下跑，錯誤會擴散到後面每一天。

1. 看它給的**具體數字**（兩邊各是多少），不要只看「哪一項沒過」
2. 先排除無害解釋：編碼差異、CRLF/LF、空白
3. 真的壞了 → 從 `01-timeline.md` 與當天的公開檔重建那一段，**不要憑記憶補**

> 上一局的 `nightlog` 覆寫就是這樣被抓到的。**你自己不會發現** ——
> 你知道全部真相，讀殘缺紀錄仍然看得懂。這正是這個檢查存在的理由。

---

## reporter 通報收到非你的訊息

有人冒充你或試圖誘導它交出底牌。

1. 確認那不是你發的
2. 從訊息內容判斷來源 —— 若是某位玩家，那是**明確的作弊實證**
3. 記入稽核紀錄，向使用者回報

---

## 有玩家說他被什麼東西擋下了

那是存取控制 hook。

1. 讀 `.claude/hooks/access.log`，找到那一筆 —— 它記著時間、session、工具與**完整參數**
2. 判斷是誤擋還是違規：
   - 他想讀 `game-state/public/` 卻被擋 → 可能是掃描範圍太大（例如整個專案的 grep），
     告訴他把範圍縮到 `game-state/public/`
   - 他直接指向 `secret/`、別人的 transcript、或 `agent-memory/` → **違規**，記入稽核
3. **不要因為他主動回報就當作沒事** —— 主動回報是他該做的，不是免責。
   但它確實是量刑的差別：回報過的與被抓到的不一樣。

---

## roster 對不上（有人讀不到他該讀的東西）

`game-state/public/roster.json` 記的是 **session id**，而 session 重啟會換 id。

- god 或 reporter 讀不到 `secret/` → 請使用者重跑 `/ur <角色>`。
  認領採**後到覆寫**，舊 id 佔著位置也會被蓋掉，不需要旗標，重跑一次就該恢復。
- 重跑後仍不行 → 不是被佔用的問題，往別的方向查。最常見的是**那個 session 跑了
  `/ur` 但沒把登記那一步跑完** —— 登記是 skill 裡的一個腳本呼叫，不是自動發生的。
  直接看 `game-state/public/roster.json` 裡那個角色的值對不對得上，
  `roster-conflicts.log` 記著每一次接管，可以對照。
- **整份 roster 不見了** → 歸檔或中止會連它一起清掉（它就在 `game-state/public/` 底下）。
  此時存取控制一律放行，要請所有 session 重跑一次 `/ur`。

---

## 你自己違反了中立性

**主動揭露，不要私下算了。**

1. 向使用者說明違規內容
2. 在該階段的公開紀錄中記載
3. 修正 `god-dispatch` 的模板，避免再次發生

> 修模板而不是「下次小心」—— 上一局的偏袒是即興產生的、隨機的，靠自律擋不住。
