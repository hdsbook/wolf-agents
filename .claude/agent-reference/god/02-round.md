# 工作流程：一輪對局

**情境**：開局已完成，正在跑第 N 天的循環。執行面的步驟在 `/god-night`、`/god-day`、`/god-vote`；這份文件放的是循環的骨架與理由。

## 速覽

| 階段 | skill | 關鍵守則 | 產出 |
|---|---|---|---|
| 夜間三階段＋結算 | `/god-night` | 第 2 夜起三階段一次跑完才回報；nightlog 累積式 | `nightlog.json`、`potions.json`、劇透版報表 |
| 天亮公布 | `/god-day` 階段 4 | 只報死了誰；發言順序隨機並公告；用程式判勝負 | `mailbox/d{N}-dawn/`、兩份報表 |
| 發言輪 | `/god-day` 階段 5 | 你不讀、不寫、不轉述發言；通知 reporter 送完就走 | `mailbox/d{N}-speak-{K}/`、逐字稿（reporter 產） |
| 投票 | `/god-vote` | 唱票用腳本核對；PK 再平即流局；用程式判勝負 | `04-votes-dayN.md`、`day_votes` |
| 每階段前後 | 全部 | 開始前比對 ref；結束後固定更新狀態檔 | `02-status.md`、`01-timeline.md` |

## 編排

```
/god-night   夜間三階段 ──→ /god-day   天亮+發言 ──→ /god-vote  投票唱票
     ↑                                                    │
     └────────────────── 天數+1 ←───────────────────────────┘
```

**循環裡沒有稽核。** 稽核只在終局跑一次（或出現可疑跡象時），
每夜跑會把對局節奏拖垮，而 hook 的即時攔截紀錄是累積的，晚一點讀不會遺失。

分出勝負時，`/god-day` 或 `/god-vote` 會直接轉向 `/god-endgame`。

## 每階段開始前：檢查 session

用 `ListAgents` 比對各 ref 與 `02-status.md` 的基準。
**ref 變動 → 該 session 重啟過** → 走 `06-incident.md` 的重啟處理。

## 每階段結束後：固定三件事

1. 更新 `02-status.md` —— 天數、存活、剛完成什麼、**下一步是什麼**
2. 追加 `01-timeline.md`
3. 更新 `secret/*.json`（直接寫，無加解密）
4. 向使用者回報 → 依節奏參數決定是否暫停（見下面兩節）

**第 3 項最容易漏。** 判準：剛剛有任何機密狀態改變嗎？有就封存。

## 依節奏參數決定是否暫停

**「暫停」＝等使用者的下一則訊息**。


| 參數值        | 停在哪裡                                   |
| ---------- | -------------------------------------- |
| 每階段暫停      | 每個階段回報之後，要進入下一階段前都停，讓使用者可以先看清楚回報訊息，再繼續 |
| 每天暫停       | 只在投票結算後（一天結束）停一次；一天之內的階段不停             |
| **全自動到結局** | **不停**，一路跑到分出勝負                        |


## 你還會在什麼時候暫停

除了上面那些暫停點，以下時間點，你也會停下來等待，**等一則一定會送來的訊息**：


| 你在等什麼               | 誰會向你傳訊息                            |
| ------------------- | ---------------------------------- |
| 開局的報到               | 玩家與 reporter 載入完會向你報到，你會等著收完所有人的報到 |
| 玩家的夜間行動、發言落檔回報、投票   | 等待玩家的回報                            |
| 參數卡片、「天黑請閉眼」這類選項的答覆 | 等待使用者回報                            |


最容易誤停的位置：

- **剛把指派送給 reporter** —— 指派後請繼續走你的流程，不用等待。
- **剛寫完檔案、剛更新狀態檔** —— 直接繼續下一個流程，除非節奏參數值是每階段回報都要暫停。



## 一輪之內的資訊流


| 階段  | 誰知道什麼                |
| --- | -------------------- |
| 夜間  | 只有行動者知道自己做了什麼；你知道全部  |
| 天亮  | 全場知道**誰死了**，不知道死因與身份 |
| 發言  | 逐字稿對後發言者公開，即時落地成公開檔  |
| 投票  | 唱票後**票型與所有理由全部公開**   |


**票是最誠實的證據**，所以理由必須原文公開 —— 那是玩家隔天推理的主要素材。

## 發言順序為什麼要隨機並公告

上一局有玩家被質疑「挑了全天最安全的發言位」，而事實是順序由上帝隨機指派、玩家無法選擇 —— 公告這點能避免無謂的爭議。

## 發言輪你為什麼不碰文字

`/god-day` 規定你在發言輪不讀發言內容、不寫 `03-speeches-dayN.md`、不整理票型指向。

> 這三條是這次改動的全部重點。上一版你在發言輪要處理同一批文字四次
> （貼逐字稿、收原文、重打進檔、向使用者轉述），九個人跑完接近五十趟往返，
> 而其中**沒有一項需要主持人的判斷**。判斷在裁決與勝負檢查，那些跟文字量無關。

`filed_list`（必讀清單）是玩家「有沒有漏讀」的唯一判準，**必須完整且正確**。
你手上有全部的落檔回報，這是你在這個階段唯一真正要維護的狀態。

## 什麼時候該懷疑自己跑錯了

- 存活人數與 `02-status.md` 對不上 → 停下來重算
- 票數總和 ≠ 存活人數 → 有人漏投或重複計算
- 角色數不是 3/3/1/1/1 → 底牌被改壞了，讀 `secret/roles.json` 核對
- reporter 通報一致性檢查未過 → **停下，不要繼續推進**，先查那一項
